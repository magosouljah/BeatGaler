# Web account isolation: local verification

The production baseline (`468a2db601a511fb4f646ac54531c000dcec74ee`) stored presentation beats at `beatvault:library:v1` and playback routes at `beatgaler:web-playback-routing:v1`. Both keys were shared by every account in one browser profile. A remembered-session marker let `AuthExperienceGate` mount the workspace before `/auth/session` returned; `useLibraryState` then copied the shared beats into React state. The later authoritative INDEX reload replaced that state, explaining the temporary A card under B.

During the 2026-10-24 A→logout→B reproduction, Vite at port 1420 was verified to be serving this `beatvault-prod-web` worktree. A clean Chrome Incognito reproduction still showed A's cached card after B had authenticated, proving the issue was in the current account/cache flow rather than stale browser application code. The gate showed the auth screen after logout, so the A card seen under B was reintroduced by B's cache read rather than surviving as the same mounted React card.

The Web keys now use `user.id`: `beatvault:library:v2:<encoded user.id>`, `beatgaler:web-playback-routing:v2:<encoded user.id>`, and `beatgaler:active-cloud-uploads:v2:<encoded user.id>`. Cache Storage thumbnail request keys also contain `user.id`. The old unowned Web keys are neither read nor migrated, because their owner cannot be proved. Desktop keeps its existing keys. There is no IndexedDB library cache in `src`.

The Web presentation payload is now `{ version: 2, owner_user_id, beats }`. The routing payload keeps its existing `version: 1` shape and adds `owner_user_id`. Each read checks that the payload owner equals the in-memory confirmed `user.id`, even when the storage key is scoped to that user. Old v2 payloads without an owner and payloads copied into another user's key are cache misses. The startup coordinator uses the same validated presentation reader as the gallery; it never parses the cache directly. A's valid physical cache remains available when A signs in again. New cache writes are skipped if their initiating account is no longer active.

`AuthExperienceGate` mounts the workspace only after a confirmed `user.id` and keys the workspace by that ID. Logout invalidates the in-memory identity and synchronously unmounts the workspace before the network logout begins. A stale restore is ignored using the account generation and gate run number. Web library reloads and late route recovery check that the initiating account is still active before publishing to the visible app.

The entrypoint starts route-free Direct connection work in parallel with `/auth/session` for a remembered session. This connection uses the current browser cookie, so it can fail if that cookie has expired; an invalid session disconnects it. A fresh sign-in constructs the route-free client and resolves the API origin alongside `/auth/login`, then connects after login establishes its cookie. Media prefetch needs the confirmed `user.id` because local startup routes and the Cloud vault are account-specific. `WebStartupPlaybackCoordinator.start()` reuses any remembered-session connection already in progress, then selects only that user's routes. It checks the account generation again after connection before prefetching media.

Local trace markers include `AUTH_SESSION_START`, `AUTH_SESSION_CONFIRMED`, `CACHE_READ_START`, `CACHE_READ_READY`, `PREFETCH_START` (`transport` or `media` phase), `PREFETCH_READY`, `PLAYABLE_READY`, and `FIRST_CORRECT_GALLERY_RENDER`. Dev-only `CACHE_OWNER_READ`, `CACHE_OWNER_ACCEPT`, and `CACHE_OWNER_REJECT` include `cache_kind`, `owner_user_id`, and `confirmed_user_id` at the identity boundary. Do not share those lines outside the local debugging session without redacting IDs. Traces contain no beat titles or media bytes. All use the existing `[play-trace]` clock with `ts_ms`. Compare timestamps within one run; `PLAYABLE_READY` means the first media prefix finished, not that audio was clicked or heard. An empty gallery has no first-card or playable marker.

The component and coordinator tests use controlled accounts and a delayed auth response to prove no A render while B is pending, B cache reuse, uncached B loading, rejection of mismatched and unowned cache payloads, no A prefetch under empty B, expired sessions, A reuse, rapid switches, and pre-auth Direct connection reuse. They do not measure Telegram or browser latency. A real before/after latency claim needs the same prepared test accounts, browser profile, network, and backend on both revisions; no such credentials or saved profile are included in this worktree.
