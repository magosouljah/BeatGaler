### Comandos

- **`inspect --environment <id> [--user] [--auth-json] [--out] [--allow-write-role]`** (§4.1): `SET TRANSACTION … REPEATABLE READ READ ONLY`; exige rol sin `UPDATE` sobre `vaults` (STOP-ENV `INSPECT_ROLE_CAN_WRITE`; `--allow-write-role` solo en laboratorio desechable). Por vault: puntero/pin, `library_beats`, cuota, purges (total/abiertas), reservas, uploads PROJECT, copias legacy, operaciones Direct en vuelo, capacidades vivas, garbage/observations, fila de catálogo, chats registrados, cuarentena; con `--auth-json`, divergencia **R12** (`vaults.id` determinista del importador y chat). `inventory_sha256` por vault y global cubren **solo SQL** (recalculables bajo lock). `telegram: "NOT_QUERIED"` siempre (`--telegram` se rechaza). `discardable: []` lo rellena el propietario fuera de la CLI.
- **`activate --manifest --auth-json [--apply]`** (§3.1, §5.0): en una transacción (apply: `LOCK TABLE catalog_native_activation`): sin activación previa (misma `environment_id` + mismo `manifest_sha256` → `ALREADY_ACTIVATED` no-op; otra → STOP-CONTRACT), rol actual ≠ rol antiguo, cutover `READY`, JSON-compat = SQL (número y hash de users y de `[user, vault_id, chat]`), 0 usuarios en cuarentena, inventario global = `inspect.inventory_sha256`, sin divergencias R12, `catalog_libraries` vacía salvo staging LEGACY listado, `pg_roles.rolcanlogin=false` y 0 backends en `pg_stat_activity` para el rol antiguo, bots registrados sin cuarentena ni rotación pendiente, `instance_inventory` no vacío y todo `stopped`, `direct_token_exposure ∈ {ROTATED, FRESH_BOTS}` (`WAIVED_TEST_ONLY` → STOP-CONTRACT). Dry-run devuelve el plan y `writes: 0`.
- **`rebind-chat --manifest [--auth-json] [--apply]`** (§4.3, §6.2.5): vault bloqueado; `vault_id` igual (R12 → STOP-DATA), chat actual = `from_chat_id`, destino libre (ni en `catalog_library_chats`, ni en otro vault, ni en la auditoría), 0 operaciones Direct/catálogo en vuelo, JSON-compat coherente si se pasa. Apply: con fila de catálogo inserta `catalog_chat_rebinds` OPEN (el trigger 0027 lo ve en la misma transacción) → escribe `vaults.telegram_chat_id` por el escritor del control-plane (misma sentencia que el flusher) → en POSTGRES: CURRENT→RETIRED, nuevo CURRENT, época+1 y revisión+1 → APPLIED → cuarentena del usuario resuelta `REBIND` → auditoría → `storageChatId` del JSON-compat reescrito **antes del COMMIT**.
- **`reset --manifest [--apply]`** (§4.2): vault bloqueado; fila POSTGRES → `ALREADY_APPLIED` solo si la generación RESET activa registra el mismo `manifest_sha256`, si no `LIBRARY_ALREADY_NATIVE` (**un reset nunca vacía una biblioteca nativa**); hash del inventario recalculado bajo el lock (≠ → STOP-DATA `INVENTORY_CHANGED`); 0 operaciones legacy en vuelo; el vault ya apunta a `new_chat_id` **y** existe auditoría `legacy→new` de `rebind-chat` (si no, `VAULT_CHAT_NOT_REBOUND` / `REBIND_AUDIT_MISSING`); chat nuevo no registrado. Apply: generaciones existentes → RETIRED (transiciones 0026, sin DELETE) → `reset-<uuid>` `origin='RESET'`, `snapshot_id='reset:<uuid>'`, descriptor canónico con lo abandonado (chat legacy, puntero, cuota, conteos, hash del ledger, hashes de manifiesto/inventario, rebind) → biblioteca POSTGRES con era nueva y época+1 (o INSERT como §3.4) → chat legacy `LEGACY_ABANDONED`, nuevo `CURRENT` → capacidades Direct revocadas → `index_bootstrap_pending=false`. **No borra** filas legacy, medios ni INDEX (T24-N).

## 2. Decisiones D-T17

- **D-T17-1:** `catalog_chat_rebinds` exige fila de catálogo (FK), pero un vault "en reset" no la tiene; la prueba de que el chat lo cambió `rebind-chat` (§4.2 paso 4) es la auditoría 0034, append-only y con destino único. Con fila de catálogo se escriben ambas.
- **D-T17-2:** "ruta de escritura del control-plane" = la misma sentencia de upsert del flusher sobre `vaults` dentro de la transacción del rebind (en modo postgres el JSON es virtual y se deriva de SQL) más la reescritura atómica del `accounts-data.json` si se pasa `--auth-json`, antes del COMMIT. Un escritor alternativo es inyectable (`controlPlaneWriter`).
- **D-T17-3:** el hash de inventario cubre solo SQL; la comparación JSON (R12) se informa aparte. Por eso `reset` exige el hash **posterior** a `rebind-chat` (secuencia documentada), lo que convierte un rebind no revisado en `INVENTORY_CHANGED`.
- **D-T17-4:** el cerco §5.0 se verifica en lo que SQL puede probar (rol NOLOGIN, 0 backends, bots, inventario de instancias declarado); la revocación real de tokens sigue siendo evidencia de T11 fase B (`token_rotation_proof_ref`, `transport_fence_proof_ref` son referencias obligatorias, no pruebas).
