# 0.9.0-beta.1 readiness

This document materializes the internal F4/25.2 beta-readiness artifacts. It does not authorize a public release and does not claim signing, notarization, provider, hardware, or production results.

## Entry criteria

A beta test session may start only when all of the following are evidenced for the candidate being tested:

- candidate identity (version and exact commit SHA) is recorded;
- required CI for that exact candidate is green;
- there are zero known P0 defects;
- there is no known P1 defect affecting a core journey;
- the tester can identify the target platform and build under test;
- known external gaps (for example signing/notarization, provider or hardware coverage) are recorded as gaps rather than treated as passes.

If an entry criterion is not evidenced, record `BLOCKED` and do not infer a pass.

## Beta test script

For each platform/build that is actually available, execute only journeys supported by that build and record literal evidence:

1. Launch the candidate from a clean application start. Record whether startup completes and the visible version/build identity.
2. Authenticate using the supported account flow. Record success/failure without storing credentials or tester PII.
3. Open Library and exercise navigation among the available library surfaces. Record whether navigation remains usable.
4. Import or add a representative supported item using the platform's available flow. Record outcome and any user-visible error.
5. Open the Drawer/Player path for a representative item and exercise the available playback controls. Record outcome; do not mark unsupported journeys as passed.
6. Open Settings and verify the available settings surface renders and can be exited without losing navigation state.
7. Exercise Setup only where the build exposes it; record completion, cancellation, or blocker.
8. Restart the application/browser where meaningful and record whether the expected non-secret user state persists.
9. Record every defect using the P2/P3 backlog form below, or escalate to P0/P1 if severity requires it.

## Result form

One result record per platform/build/session:

```text
CANDIDATE_VERSION:
CANDIDATE_SHA:
PLATFORM:
BUILD_ID_OR_ARTIFACT:
SESSION_DATE_UTC:
ENTRY_CRITERIA: PASS | BLOCKED
JOURNEYS_EXECUTED:
JOURNEYS_NOT_COVERED:
RESULT: PASS | FAIL | BLOCKED
DEFECT_IDS:
EVIDENCE:
EXTERNAL_GAPS:
NOTES:
```

Do not include credentials, tokens, private keys, tester names, email addresses, device identifiers, or other tester PII.

## P2/P3 beta backlog

Use this compact backlog for non-P0/P1 beta findings. P0/P1 findings are release-gate defects and must not be downgraded to fit this table.

| ID | Severity | Platform | Journey | Summary | Reproduction/evidence | Candidate SHA | Status |
| --- | --- | --- | --- | --- | --- | --- | --- |
| _none recorded_ | — | — | — | No P2/P3 beta findings have been evidenced in this artifact yet. | — | — | OPEN |

Severity guidance:

- `P2`: material degradation with a viable workaround; does not make a core journey unusable for the beta cohort.
- `P3`: minor/cosmetic/polish issue with low functional impact.

Allowed status values: `OPEN`, `FIXED_PENDING_VERIFY`, `VERIFIED`, `DEFERRED`. `DEFERRED` requires an explicit rationale and does not erase the finding.

## Exit criteria

A beta-readiness review may exit only when all applicable conditions are evidenced:

- every executed session has a completed result form tied to an exact candidate SHA;
- zero known P0 defects remain open;
- no known P1 core-journey defect remains open;
- P2/P3 findings are recorded with owner/disposition before release decision;
- required exact-candidate CI is green;
- supported journeys have literal evidence, while unsupported or externally blocked journeys remain explicitly `NOT_COVERED`, `PENDING_EXTERNAL`, or `BLOCKED`;
- external signing/notarization/provider/hardware gaps remain explicit and are not converted into internal PASS claims;
- a release owner makes the separate release decision. Completion of this document alone is not release authorization.

## Existing artifacts reused

This readiness artifact intentionally does not duplicate implementation or release machinery. The beta review should reuse the repository's existing design foundations/components, focused component tests, F4 functional matrix, release controls, and platform workflows as their literal evidence permits.
