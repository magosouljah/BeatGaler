# F0/0.20 — OAuth secret rotation readiness

Status: **READY_FOR_OWNER_ROTATION / NOT DONE**

This runbook covers the OAuth client credential that was exposed during prior troubleshooting. It intentionally records only logical identifiers and operational state. **Never paste a current or replacement secret value into this repository, GitHub Issues/PRs, Actions logs, documentation, screenshots, or handoffs.**

## Credential identity and current boundary

- Provider: **Google OAuth 2.0**.
- Logical runtime variable: `GOOGLE_CLIENT_SECRET`.
- Matching non-secret client identifier variable: `GOOGLE_CLIENT_ID`.
- Backend consumer: `cloud-server/server-core.js`.
- Google authorization-code callback: `${BEATGALER_OAUTH_PUBLIC_BASE}/auth/oauth/google/callback`.
- The Google client secret is added only to the server-side token exchange request. It is not returned by the OAuth start endpoint and must never be compiled into Web/Desktop frontend code.
- `cloud-server/server-core.js` loads normal process environment configuration through `dotenv`; the repository does not hardcode the Google secret.
- The repository's AWS Secrets Manager provider currently protects the control-plane envelope keyring. It is **not** the loader for `GOOGLE_CLIENT_SECRET`.
- Therefore the current OAuth deployment contract is external runtime injection of `GOOGLE_CLIENT_SECRET`. The concrete production host secret-store/environment source that populates that variable is deployment-owned and must be verified by RO before rotation. Do not move the value into GitHub Actions to make the rotation easier.

## History boundary

F0/0.20 rotates the compromised credential. It does not rewrite Git history.

Historical purge, if the exposed OAuth material is part of the already-reported sensitive history, is handled separately by **F0/0.12 / GitHub Support ticket #4706781**. Do not force-push, rewrite history, or open a second historical-cleanup request from this task. Rotation is still mandatory regardless of the purge outcome.

## Before creating the replacement

RO must establish these facts without copying secret material into a handoff:

1. In the running production/staging service configuration, identify the Google OAuth client by the current `GOOGLE_CLIENT_ID`.
2. Confirm the Google Auth Platform client has the exact authorized redirect URI derived from the deployed `BEATGALER_OAUTH_PUBLIC_BASE` plus `/auth/oauth/google/callback`.
3. Identify the external production secret source that supplies the cloud-server process environment and confirm it can replace `GOOGLE_CLIENT_SECRET` without committing it to the repository.
4. Record only the secret-store identifier/path and deployment target. Do not record the secret value.

If step 3 cannot be established, stop with `READY_FOR_OWNER_ROTATION` and resolve the deployment ownership/configuration first.

## RO rotation procedure — preferred no-downtime path

Google's current OAuth client-secret rotation flow supports two simultaneously enabled client secrets for eligible clients.

1. Open **Google Auth Platform → Clients** in the Google Cloud project used by BeatGaler.
2. Open the OAuth 2.0 client whose client ID matches the deployed `GOOGLE_CLIENT_ID`.
3. If the client details page offers **Add Secret**, click **Add Secret**. Google shows the full new secret only at creation time.
4. Store that new value immediately in the existing external production/staging secret source as the value supplied to runtime variable `GOOGLE_CLIENT_SECRET`. Never put it in source control or GitHub Actions.
5. Redeploy/restart only the BeatGaler cloud-server service/configuration required for the environment change. Do not change the client ID, redirect URI, scopes, product policy, or release state as part of this rotation.
6. Run the verification checklist below while the old secret remains enabled.
7. After the new credential is verified and rollout evidence shows the old secret is no longer in use, return to the same Google OAuth client and click **Disable** for the older secret.
8. Re-run the verification checklist. A disabled secret should be rejected by Google OAuth flows; do not restore or log the old value merely to prove this.
9. When the service remains healthy with the new secret, click **Delete** for the disabled old secret. Deletion is the final retirement step.

Google permits at most two client secrets. If two already exist, inspect creation/status metadata without exposing values and retire the known-unused one before creating another.

## Atomic fallback when the client only offers Reset secret

Some Google credential surfaces may present **Reset secret** rather than dual-secret rotation. If **Add Secret** is unavailable:

1. Prepare the external secret destination and deployment command/restart path first.
2. Enter an owner-approved short maintenance/rotation window because resetting immediately invalidates the previous secret.
3. On the affected OAuth client, click **Reset secret** and confirm the reset.
4. Store the new value immediately as `GOOGLE_CLIENT_SECRET` in the external runtime secret source.
5. Redeploy/restart the cloud-server service immediately.
6. Run the complete verification checklist.
7. Record only success/failure, client logical identity, deployment target, and timestamps. Never record the generated value.

## Verification checklist after deployment

Evidence is complete only when all applicable checks pass without secret material in output:

1. Cloud server starts cleanly and no OAuth credential material appears in service logs.
2. `POST /auth/oauth/start` for Google returns a Google authorization URL and the expected callback flow; no client secret appears in the response.
3. Complete a fresh Google sign-in through the Web login UI.
4. Confirm Google returns to `/auth/oauth/google/callback` successfully and the authorization-code token exchange succeeds.
5. Confirm the OAuth polling/session flow completes and the expected BeatGaler account is created or signed in.
6. Confirm an authenticated account/session request succeeds after OAuth completion.
7. If Desktop uses the same cloud backend for account OAuth in the deployed build, complete the same fresh Google sign-in from Desktop and confirm the shared callback/session path succeeds.
8. Confirm no browser/network payload or frontend bundle contains `GOOGLE_CLIENT_SECRET` or any generated secret material.
9. Confirm the F0/0.20 HEAD secret-scan workflow is GREEN.
10. After disabling the old Google secret, repeat a fresh Google OAuth login. Google documents that disabled client secrets are rejected; successful fresh login after the disable is evidence that the deployment is using the new secret.
11. Delete the disabled old secret only after these checks remain GREEN.

Google refresh-token rotation is not required by this task: the compromised item is the OAuth **client secret**, not a user refresh token. The current Google login path uses the client secret for the authorization-code token exchange. Do not revoke user grants unless separate evidence requires it.

## Close criteria

F0/0.20 may move to **DONE** only when all of the following are evidenced without exposing secret values:

- replacement Google client secret created;
- replacement stored outside the repository;
- staging/production cloud-server is using the replacement;
- Web OAuth login, callback, token exchange, and account/session flow succeed;
- Desktop OAuth succeeds too when it shares this backend path;
- old secret disabled and then deleted/revoked;
- fresh OAuth still succeeds after old-secret disable;
- HEAD secret scan is GREEN;
- no sensitive values appear in logs, PR, docs, issue, or handoff.

Until RO completes the provider-side creation/deployment/revocation steps, status remains **READY_FOR_OWNER_ROTATION / NOT DONE**.
