# PROJECT de 1.9 GB: implementación aislada para Fase 4

Estado: **implementado en `prep/phase4-public-launch`; todavía sin S3/RDS/Telegram real ni ensayo de 1.9 GB**. No se ha integrado en Fase 3, STEP 14 o STEP 15, ni desplegado. El límite comercial son `1_900_000_000` bytes decimales; el máximo se divide en 114 partes de hasta 16 MiB.

El adaptador MASTER existente usa `CustomFile` de GramJS desde una ruta de disco. La versión instalada lee cada parte desde el fichero con un buffer acotado (a este tamaño, 512 KiB y 3,624 partes Telegram), sin convertir los 1.9 GB en un único `Buffer`. El límite efectivo y los timeouts de Telegram todavía requieren prueba real.

## Contrato que se conserva

El navegador sólo obtiene URLs firmadas para partes de un objeto privado de staging. Staging nunca es una referencia de biblioteca. El worker vuelve a medir **todos** los bytes y SHA-256 al leer el objeto completo; `project-upload-authority.js` vuelve a medir el fichero local y comprueba su `stat`, autorización vigente, vault, purge pendiente, mensaje MASTER y documento Telegram. Sólo su recibo PostgreSQL de `library_project_uploads` permite que `project-access.js` acepte el PROJECT nuevo o reemplazado en el INDEX. La recuperación de MASTER por beat y SHA evita duplicar el documento tras una caída entre el envío Telegram y el commit PostgreSQL. La lectura, downgrade y purge usan los mismos recibos y verificaciones de STEP 5/6.

## Flujo preparado

1. Web conserva la operación Direct con capability del beat. Para importación, la reserva de cuota del beat precede al PROJECT. El API exige usuario autenticado, vault propio, beat existente o reserva vigente sin purge, Access del plan actual, tamaño máximo, un único PROJECT activo por usuario y máximo 12 sesiones nuevas por hora; reanudar la misma sesión no gasta otra admisión. Registra una sesión idempotente de 24 horas en la migración `0019`.
2. Web calcula SHA-256 de cada slice de 16 MiB con memoria acotada, forma una huella de la secuencia de checksums, y conserva el identificador en `localStorage`. El API firma PUT de partes S3 con checksum SHA-256 **y `Content-Length` exacto** ligados a la firma; el navegador envía el largo implícito de cada `Blob`. Web envía como máximo tres partes en paralelo. El proxy de 2 MB sólo recibe solicitudes JSON pequeñas; los bytes van por HTTPS directamente a S3. Al reabrir, `ListParts` permite omitir las partes cuyo tamaño y checksum coinciden. Una parte interrumpida se reenvía, nunca el archivo completo.
3. El API coteja número, tamaño y checksum de las 114 partes como máximo antes de `CompleteMultipartUpload`, confirma `HeadObject` por tamaño y pone la sesión en `READY`. Si se pierde la respuesta de S3 después del commit, `HeadObject` permite continuar sin repetir la subida.
4. Un worker toma una sesión con `SKIP LOCKED`, lease PostgreSQL y lock advisory global para limitar a **un envío Telegram simultáneo** entre procesos. Descarga de S3 a un directorio privado con streaming, espacio libre comprobado (`tamaño + 2 GiB`) y timeout por falta de avance. Al reiniciar, puede reclamar de nuevo tras vencer el lease; reusar el recibo/asset MASTER existente evita duplicados. Conserva S3 para un retry si falla descarga o Telegram. Tras el recibo confirmado elimina S3 y el fichero local. Una limpieza periódica aborta MPUs abandonados, elimina objetos completos sobrantes y retira directorios temporales huérfanos de más de 24 horas sólo bajo el lock global; el lifecycle del bucket cubre caídas del proceso.
5. Web espera el resultado del worker y sólo entonces continúa la publicación INDEX original. Mientras el worker procesa, el editor muestra “Finalizing PROJECT in Galer Cloud…” en vez de aparentar una subida terminada al 100 %. El recibo devuelto mantiene el formato `direct-web`, por lo que las rutas de recuperación/lectura posteriores no cambian. Si el navegador se cierra, un nuevo intento con el mismo ZIP y beat consulta la sesión y continúa. Un `FAILED` puede reintentarse con el objeto S3 existente, sujeto a Access vigente.

## Infraestructura exacta pendiente de provisionar

- Un bucket S3 privado exclusivo de staging y KMS key en la región del Cloud host. `deploy/project-staging/bucket.yaml` declara bloqueo público, cifrado KMS, CORS para el origen Web, permiso mínimo para el rol Cloud, abort de multipart incompleto a 2 días y expiración de objetos completos a 7 días. Revisar el ARN del rol y origen real antes de crear el stack. No hay credenciales AWS ni recursos creados aquí.
- Un volumen temporal **cifrado**, montado en el host del worker, con al menos 3.9 GB libres para un archivo máximo más reserva; dimensionar **20 GB mínimo** para sistema, logs, reintentos y margen. Fijar `PROJECT_STAGING_TEMP_DIR` en ese mount con permisos de acceso sólo del proceso. El preflight comprueba espacio actual y acceso al bucket, pero no certifica cifrado del volumen, KMS de lectura/escritura ni CORS: esos son ensayos reales.
- PostgreSQL productivo con migración `0019` y pool `max >= 2`; el mismo rol Cloud requiere permiso KMS. Variables: `PROJECT_MULTIPART_ENABLED=true`, `PROJECT_STAGING_S3_BUCKET`, `PROJECT_STAGING_AWS_REGION`, `PROJECT_STAGING_KMS_KEY_ID`, `PROJECT_STAGING_TEMP_DIR`. En producción `/readyz` falla si el staging requerido no está preparado o el worker no está sano. El feature flag permite mantenerlo cerrado hasta que esté provisionado.

## Prueba de aceptación antes de anunciar 1.9 GB

En staging equivalente al host público, aplicar migración y stack, verificar CORS/KMS y que el navegador envía `Content-Length` en un PUT firmado real, después subir un ZIP de **exactamente** `1_900_000_000` bytes desde Web por el proxy público. Interrumpir Web a mitad y reiniciar sin reenviar partes confirmadas; cortar el worker después de `CompleteMultipartUpload` y durante Telegram, comprobar reanudación y un solo recibo utilizable. Comparar SHA-256 local con `library_project_uploads` y el documento Telegram, publicar INDEX, descargar y verificar hash, restaurar tras downgrade a Free (lectura sí; nuevo PROJECT no), hacer purge y comprobar borrado de documento/recibo según STEP 6. Medir RSS, disco libre, ancho de banda, duración, timeout, costes S3/KMS y tiempo de recuperación. Ensayar dos tenants y dos proyectos del mismo usuario para comprobar aislamiento y admisión; forzar falta de espacio, revocación del plan y CORS/KMS denegados. Ninguna prueba local con mocks sustituye esta evidencia.

Antes de rollback de Cloud a un binario sin worker, drenar `READY`/`PROCESSING` y comunicar que un `UPLOADING` puede necesitar terminar después del rollback; sus partes S3 caducarán. Recibos ya confirmados y referencias INDEX son compatibles con el servidor anterior. Monitorizar sesiones `READY`/`FAILED`, edad de `PROCESSING`, bytes de staging, aborts/cleanup fallidos, errores KMS/S3, espacio libre y tiempo Telegram. Alerta humana y restore de RDS siguen siendo gates de Fase 4.
