- **Web es V1.** `WEB_FOUNDATION_CAPABILITIES.youtubePublishing=false`; la UI de YouTube/Bulk depende del helper Desktop. YouTube y Bulk quedan fuera del gate de lanzamiento Web y no deben anunciarse allí. Sus cuotas declaradas en la política no prueban disponibilidad Web. Anual no se vende: precio y política pendientes.
- Welcome: grant interno Paid Entry de 7 días, una vez al activar/verificar la cuenta; no es trial del proveedor y una compra pagada no retrasa el cobro. En PostgreSQL V1 lo emite Access tras verificación de email o identidad OAuth confirmada; el modo JSON legacy conserva su comportamiento anterior.
- Pago confirmado, no redirect ni estado del proveedor, habilita el período. Cambio Paid Entry ↔ Highest Paid en el próximo período **pagado**, sin prorrateo inmediato. Cancelación normal o downgrade a Free al fin de cobertura pagada. Renovación fallida: 7 días de grace desde `past_due_at`, sin elevar un upgrade pendiente.
- Downgrade, cancelación y refund no borran datos. Beats existentes siguen utilizables; si activos + Trash exceden el nuevo cupo, se bloquean identidades nuevas hasta volver bajo cuota. Free conserva PROJECT pero no puede subirlo ni reemplazarlo. Refund completo confirmado del período vigente revoca esa cobertura; parcial no la revoca por defecto; refund histórico no revoca otro período vigente.
- Sin límite **comercial** de dispositivos o sesiones en V1. Controles técnicos y de seguridad siguen independientes. `plans.js` aún expone límites comerciales y tamaños PROJECT distintos: no es el contrato de venta.
- Trash cuenta en el cupo. Move/restore conservan la identidad; el purge de Cloud se confirma sólo tras verificar con MASTER la ausencia de los mensajes referenciados (incluidos PROJECT y recibos asociados). Web escribe `purge_after` a 14 días, pero no ejecuta un scheduler propio; Desktop conserva su disparador automático. Ningún evento Billing provoca purge.

## Evidencia y gates abiertos

Son pruebas unitarias/de contrato y sintaxis; **no** se ejecutó PostgreSQL E2E ni Polar real en esta auditoría. Existen migraciones Billing `0006`–`0008` y `0011`–`0013` (última migración general: `0014`) y suites PostgreSQL aisladas; su existencia no certifica la app integrada. El runner histórico Polar se detiene con `BILLING_E2E_REAL_RENEWAL_ACCELERATION_UNAVAILABLE`. El estado local ignorado de la corrida diaria `20260912123817_e7cfaa52` (SHA `8943436`, `PARTIAL`) registra un segundo Order pagado, pero `DAILY_REAL_RENEWAL_WEBHOOK_REQUIRED`; no es PASS de renovación ni de Fase 3 E2E.

**STEP 1 (2026-10-08; base `bc99e593f9607c74a919a81c0207894db600b7e8`):** En la autoridad PostgreSQL, el snapshot Auth persiste cuentas/sesiones/proveedores/MFA/vaults sin reconstruir grants. `planState` es sólo una proyección de lectura legacy; un snapshot Auth obsoleto no cambia filas Access, identidad ni fechas. El import de entitlements queda aislado al cutover anterior a `READY`; exportar a JSON excluye grants revocados. Welcome se inserta una vez por usuario con el índice único existente; un fallo al emitirlo durante la verificación permite reintentar. La UI y `/plans/me` aún usan `plans.js`: sustituir esa lectura por el resolver V1 pertenece a STEP 2. La suite amplia Cloud conserva un fallo Direct ajeno a este cambio (`direct-persistent-legacy-lazy.test.cjs` exige un fake `probeSessionMembership`).

**STEP 2 (2026-10-08; base `832ec952d2f15a4307056dff818202946a65c370`):** Duplicación hallada: `plans.js` calculaba Paid/Free desde `basePlanId` y grants de Auth para `/plans/me`, Account y `/plans/catalog`; Settings marcaba el plan con `base_plan_id`. Access ahora consulta `billing_subscription_state` y `entitlements`, ejecuta `resolveBillingAccess` para cada lectura y entrega el mismo payload a `/plans/me` y todos los serializers de Auth. El catálogo PostgreSQL sale del catálogo V1; Settings marca el plan efectivo recibido. El payload conserva aliases existentes (`base_plan_id`, `effective_plan_id`, `entitlements`, `quotas`) y agrega `access` con fuentes, capacidades, fechas, grace y cambio pendiente. `base_plan_id` es sólo el plan comercial proyectado por Access, nunca una lectura de Auth. Regresiones de consumidores, PostgreSQL real, ownership STEP 1, Billing V1, Auth/control-plane y frontend enfocados verdes; typecheck verde. `plans.js` queda sólo para catálogo/estado JSON de desarrollo, welcome JSON y dev-switch JSON; el import/export legacy conserva `planState` para rollback, sin autoridad Web PostgreSQL. STEP 3 debe contar beats reales, incluidos Trash; STEP 12 debe corregir copy, checkout simulado y YouTube/Bulk Web.

**STEP 3 (2026-10-08; base `98f5ac3653da68472bc5edf5e7dd5e8e785eeb2f`):** La identidad estable es `beat.id` en `beats[]` y `trash[].beat` del INDEX fijado en Telegram. El INDEX y `vault_index_pointers` no guardaban un conteo server-side; import Web crea IDs en cliente y varios procesos podían publicar sin reservar cupo. La migración `0015` añade `library_quota_state`, `library_beats` (ACTIVE/TRASH) y `library_beat_reservations`. El bootstrap interno lee el INDEX desde el servidor con MASTER, verifica pin antes/después, valida IDs y guarda sólo identidad/estado en una transacción. Repetir con igual pin/hash no duplica; INDEX cambiado exige reconciliación y falla cerrado. Sin bootstrap, `reserve` rechaza nuevas identidades. Cada reserva/confirmación bloquea la fila del usuario en PostgreSQL y consulta el límite de `resolveBillingAccess`; used incluye ACTIVE + Trash, y pending ocupa capacidad. Reserva, confirmación, cancelación, denegación y expiración son durables e idempotentes por usuario/operación. La expiración libera pendientes tras 15 minutos; una confirmación revalida el plan para impedir alta tras downgrade. Pruebas PostgreSQL reales cubren 19/20, 99/100, Highest, usuarios aislados, Trash, retry, restart, downgrade y expiración. **STEP 4 debe conectar esta primitiva a todas las rutas de creación/INDEX y reconciliar un INDEX que cambie después del bootstrap.** Hasta entonces las operaciones actuales no están bajo enforcement de cuota. No se conectó ninguna ruta nueva.

**STEP 4 (2026-10-08; base `e2fda7edf889c9a328e61994017307e6aebe5fb8`):** Import Web obtiene una reserva idempotente `new:<beat.id>` con capability `commit_import` antes de subir media y la renueva mientras dura la carga. Todas las escrituras Web del INDEX (bootstrap, import, edit, move, restore y purge) usan `replace_index` y publican por MASTER desde el servidor. La ruta comprueba usuario/vault/capability, pin anterior y hash del ledger, estado ACTIVE+Trash, tombstones de purge, reservas vigentes para **cada** ID nuevo y el límite actual de Access; sólo entonces fija el INDEX y confirma identidades, estados y puntero en PostgreSQL. Una edición o movimiento de identidad existente no consume slot. El bot Direct ya no recibe permiso `pinMessages`; la migración `0016` registra el bot READY al que MASTER le revocó ese permiso antes de entregar credenciales nuevas. El arranque repara un pin sin commit desde la copia confirmada, y un retry tras commit devuelve el mismo INDEX/beat/slot. `/transport/index/commit` no acepta un puntero alterado que no coincida con el pin y el ledger. Pruebas PostgreSQL aisladas cubren dos **procesos** compitiendo por 19/20, INDEX manipulado, crash entre pin y commit, retry, edición/Trash en 20/20, purge manual, downgrade 21/20 y pending tras downgrade; STEP 3, capabilities Direct, typecheck, build Web y Billing V1 siguen verdes. Telegram se sustituyó por un transporte inyectado en la prueba PostgreSQL; la corrida con Telegram real y el E2E final siguen en STEP 15.

**STEP 5 (2026-10-09; base `0ac910e2d64001a4ceb2be6d1e67390801283d8e`):** Import/edit Web hacen preflight de PROJECT con Access V1. `/transport/project/upload` exige capability del beat, recibe multipart, corta en el primer byte excedente, cuenta/hash del stream guardado y publica el documento por MASTER. La migración `0017` guarda recibos por usuario/beat/hash/documento; el INDEX sólo admite PROJECT nuevo o reemplazado con recibo verificado y tamaño coincidente. La reserva STEP 4 es obligatoria para un beat nuevo; errores la cancelan, y los reintentos recuperan un asset MASTER o un pin sin commit sin duplicar beat ni slot. PROJECT heredados de una o varias partes se copian como mensajes de MASTER antes de entregar una sesión Direct, con referencias nuevas y recibos de migración atómicos con el INDEX. Una marca de migración falsificada sin recibo PostgreSQL no se acepta. Los bots Direct existentes reciben de nuevo derechos sin `editMessages`, `deleteMessages` ni `pinMessages` antes de esa migración; los nuevos nacen con esos mismos derechos. El PROJECT permanece legible y la metadata editable tras downgrade; Free no puede cambiarlo. Pruebas con PostgreSQL real y Telegram simulado cubren A–M, dos partes heredadas, caída entre pin y commit, copia reutilizada, derechos de bots anteriores y límites decimales. La ruta HTTP multipart comprueba el borde exacto y el primer byte excedente; pasan typecheck, build Web, suites de import/edit/download/capabilities y Billing V1. No hubo Telegram real: la copia dentro del mismo vault y la revocación de derechos deben observarse en el E2E de STEP 15; si falla, el arranque/sesión cierran antes de entregar Direct. No se inició STEP 6.

**STEP 6 (2026-10-09; base `2446e276d355044baf944504571859a0d4747040`):** El purge Web anterior quitaba el beat del INDEX y de `library_beats` antes de llamar a `deleteMessages` con el bot, y ocultaba el error. Desktop también fijaba primero un INDEX reducido y después intentaba borrar media; Topic cleanup era una cola posterior. La migración `0018` guarda `library_trash_purges` por `(user_id,beat_id)` con operación estable `purge:<beat_id>`, estado `PENDING`/`CONFIRMED`, snapshot de IDs, hash del beat y error reintentable. Tombstones históricos se importan como `LEGACY_TOMBSTONE`: impiden reutilizar el ID sin afirmar falsamente que sus mensajes fueron verificados. El servidor toma el beat sólo del INDEX confirmado, rechaza assets sin localizador comprobable o compartidos, incluye master, artwork, WAV/partes, metadata, PROJECT/partes y recibos PROJECT persistidos. MASTER consulta los mensajes, borra los presentes y verifica que todos aparecen ausentes; una falla deja `PENDING` y `library_beats` sin cambios. Sólo después publica y verifica el INDEX nuevo y, en la misma transacción PostgreSQL, quita la identidad del ledger, confirma el purge y conserva el tombstone. El arranque restaura un pin sin commit y reintenta operaciones pendientes; dos purges conservan un único efecto. Publicar un INDEX quitando Trash sin este flujo, restaurar un pendiente o reutilizar un tombstone confirmado se rechaza. Web y Desktop move/restore mantienen el mismo `used`, incluso overquota; ambos purges usan la ruta del servidor. Topic cleanup se encola **después** del purge confirmado y exige su tombstone; no cuenta como prueba de liberación de cuota. La definición de “confirmado” cubre todos los mensajes vinculados en el INDEX y los recibos PROJECT PostgreSQL, no mensajes huérfanos previos que ya no tienen referencia al beat. PostgreSQL real con Telegram simulado cubre A–P, reinicio, partes PROJECT, carreras y dos tenants; typecheck, build Web, tests Rust y regresiones STEP 3–5 pasan. La observación de `channels.GetMessages`/`DeleteMessages` con Telegram real y la limpieza de Topics quedan para STEP 15. No existe scheduler Web para `purge_after`; el purge Web es manual y Desktop mantiene su disparador a 14 días.
