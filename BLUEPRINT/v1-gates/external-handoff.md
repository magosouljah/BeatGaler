# V1 external handoff after local verification

This handoff is a run order, not permission to charge, deploy, alter provider state, or write production user data. Replace `<FINAL_SHA>` only after the prep branch is frozen. Keep every artifact tagged with that exact SHA, target environment, UTC timestamp, and run ID. Never put credentials, account passwords, tokens, cookies or webhook URLs in reports.

## 1. Recover existing STEP14 evidence read only

Inputs: current Polar Sandbox credential and webhook secret, isolated PostgreSQL admin URL, E2E email, webhook transport, preserved canonical `.billing-e2e` run directory, and the existing run IDs in `step14.md`. The current WSL shell lacks the E2E variables; the canonical `.env` has Sandbox token/webhook secret and DB URL but no isolated admin URL or E2E email/transport. Validate provider token scope and DB identity before connection. Inspect existing renewal Order/Payment, provider delivery history, signed inbox receipt, Access, cancel boundary, inverse paid cycle and source SHA. Do not start `e2e:polar-sandbox` during this read-only phase. It can create a Sandbox transaction. Pass only if F1–F3 each has exact-event/Order/Payment/Access correlation and F4 has final-SHA provenance. If old evidence cannot close a gap, record it and request explicit authorization for the smallest new transaction and human hosted-payment step.

## 2. Provision and preflight production without promotion

Inputs: isolated production RDS/PostgreSQL, Secrets Manager keyring and IAM role, verified PITR, production Polar token/catalog/webhook secret, Google/X OAuth callbacks, SES sender, Telegram MASTER/manager/transport pool, durable PROJECT upload filesystem with measured free space, all 17 alert destinations, DNS/TLS, and a named on-call owner. Set `BEATGALER_SOURCE_SHA=<FINAL_SHA>` and the cutover snapshot digest in the Cloud environment. Run `node scripts/v1-deploy-preflight.mjs --production-env` under that environment. It emits only missing/invalid key names and must pass before promotion. The command does not contact providers and does not prove credential validity, live delivery, PITR, or runtime correctness. Do not use the canonical STEP14 database or temporary upload directory.

## 3. Restore, cutover and rollback proof

Create an encrypted production backup and independent isolated restore under the production backup policy. Verify migration ledger, row counts, tenant/account integrity, secret decryptability, INDEX pointers and access projections. Measure actual snapshot age, RPO and RTO against the required RPO ≤15 minutes and RTO ≤2 hours; prove PITR at a chosen timestamp. Preserve the previous Cloud/Web artifact and a database compatibility decision before switching traffic. The local `scripts/v1-local-postgres-recovery.sh --run-disposable` and `tests/v1-web-release-switch.test.sh` demonstrate only disposable mechanics. Rollback must fail closed if the prior artifact is incompatible with the migrated database; validate through `deployment-promotion-contract.mjs`. External rollback effect: traffic returns to the previous tested Web/Cloud artifact while database state remains durable and compatible. Record commands, timings, checksums and sanitized outcome in an isolated operations report.

## 4. Same-SHA public promotion and read-only smoke

Deploy Web and Cloud from the same immutable `<FINAL_SHA>`; configure `NODE_ENV=production`, `BEATGALER_DEPLOYMENT_ENV=production`, `BEATGALER_SOURCE_SHA=<FINAL_SHA>`, and production Polar provider selection. Confirm the release archive's `.well-known/source-sha.txt` and both Cloud health endpoints show `<FINAL_SHA>`. Run `BEATGALER_API_ORIGIN=https://api.beatgaler.com BEATGALER_EXPECTED_SOURCE_SHA=<FINAL_SHA> node cloud-server/scripts/post-deploy-smoke.mjs`. Then run `V1_PUBLIC_CANARY_ACK=READ_ONLY_NO_CHARGES V1_EXPECTED_SOURCE_SHA=<FINAL_SHA> V1_PUBLIC_WEB_ORIGIN=https://beatgaler.com V1_PUBLIC_CLOUD_ORIGIN=https://api.beatgaler.com node scripts/v1-public-canary.mjs`. Both commands are GET-only and fail on wrong SHA, environment, readiness or Web proxy. The 2026-10-17 read-only probe still observed public Web SHA `206bed0fb577ef7c2949390a0bd29e1a81c57aa3` and Cloud `environment=development`, so current public deployment is not the prep candidate.

## 5. Disposable public Browser and cross-account canary

Provision a dedicated disposable account with a verified vault, no payment instrument, and a documented deletion/retention owner. Set the four public canary variables above, plus `V1_PUBLIC_BROWSER_ACK=ACCOUNT_LOGIN_ONLY`, `V1_PUBLIC_ACCOUNT_DISPOSABLE=1`, `V1_PUBLIC_ACCOUNT_IDENTIFIER`, `V1_PUBLIC_ACCOUNT_PASSWORD`, `V1_PUBLIC_RUN_ID=v1-public-<unique-id>`, and optionally `V1_PUBLIC_EXPECTED_PLAN=free|paid_entry|highest_paid`. Run `npx wdio run wdio.v1-public.conf.mjs`. The harness first runs the read-only same-SHA canary, then signs in, verifies plan/account quotas and entitlements, checks that the INDEX-backed visible library and identity survive reload, and records a sanitized report below `tmp/v1-public/<run-id>/`. It removes the local browser profile. It does not create or delete the remote account; the assigned owner must perform that cleanup separately. A broader two-account public run must additionally prove ID/file denial, Free quota and Trash count, Entry/Highest PROJECT limits, Direct INDEX/media integrity, expiry and downgrade. Those tests write disposable account state and may use Telegram; assign exact accounts, fixtures and cleanup before running. The isolated `wdio.step15-real.conf.mjs` remains a local Cloud harness and is not a substitute for public HTTPS proof.

## 6. Observability and controlled financial canary

Wire the Cloud condition logs, deploy/backup runner failures and a scheduled `BEATGALER_PROJECT_UPLOAD_TEMP_DIR=<durable-dir> BEATGALER_PROJECT_UPLOAD_TEMP_BUDGET_BYTES=<measured-budget> node scripts/v1-temp-storage-check.mjs` probe to an actual collector; poll `/healthz`, `/readyz` and the authenticated Direct status outside Cloud. Configure retention and a named on-call escalation. `node scripts/v1-observability-preflight.mjs` identifies 17 route names but never sends an alert. Trigger one controlled synthetic operational alert through the real route, verify receipt and acknowledge it. Prove backup freshness and support/refund response drill. Once all nonfinancial gates pass, obtain explicit authorization stating provider environment, maximum number and amount of transactions, payment operator, target disposable account, refund plan and retention/cleanup. Only then run the final-SHA Sandbox lifecycle gaps and a controlled production purchase/refund with real signed webhook, Order, Payment, Access, idempotency and reconciliation evidence. A refund is the financial rollback; confirm it with provider and Access state. No charge, including Sandbox, is authorized by this document.

## Decision rule

Declare V1 `CLOSED/GO` only when G3–G6 and G8–G10 in `V1-CLOSURE-GATES.md` pass on the final SHA, STEP14 F1–F4 are closed, production restore/rollback and alert delivery are measured, and the public same-SHA Browser/PROJECT/tenant/billing matrix passes. Otherwise retain `NO-GO`; when every remaining item requires credentials, infrastructure, external identity/provider state, a live deployment, or explicit charge authorization, classify the remaining work as `NO-GO_EXTERNAL_ONLY` with the exact owner/action/evidence for each item.
